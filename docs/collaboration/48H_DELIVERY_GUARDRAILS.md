# 48 小时交付止损规则

> 状态：2026-09-03 用户明确要求执行
>
> 目的：剩余开发、调测和交付以“尽快得到可评分候选”为中心，防止流程、Docker 和文档工作
> 挤占模型评测与准确率调优时间。
>
> 用户声明的时间窗口：距代码提交约 48 小时。本文记录决策时的相对窗口，不自行推算官方截止
> 时刻。

## 1. 已发生的问题

B05 的公开功能面较小，但约四小时被生产级兼容性验证和容器流程放大。真实 MemOS tenant/readback
问题的发现与修复是必要工作；以下流程成本可以避免：

- 已知官方 PyPI 较慢，仍在首轮构建使用它；
- 未先检查 rootless daemon 的端口发布和 cgroup 能力，就进入完整生命周期验证；
- 小范围源码变化后反复构建镜像，而不是用原生进程或源码挂载迭代；
- 把 Docker 完整证明与核心算法 Gate 绑定，直到后期才切换为可选加分项；
- 在已有确定性证据后继续扩大验证和文档，而没有先保护端到端开发与调优时间。

结论：镜像不会在源码变化后自动更新，因此真实打包验证需要构建；但“每次修改都重新构建”不是
算法或交付要求。开发期应直接运行源码，代码冻结后才构建候选。

## 2. 剩余工作的硬优先级

按以下顺序使用剩余时间，低优先级不得阻塞高优先级：

1. **P0 可评分闭环**：完成经用户批准的剩余核心开发，使 Add、Search、Health、超时、隔离和
   错误语义形成端到端候选。
2. **P1 首个真实 baseline**：在调测机探测真实模型和 Embedding，跑通最小样本并得到第一份可复现
   分数。没有 baseline 前不做广泛调优。
3. **P2 高收益单变量调优**：模型选择、prompt 和 Search/证据策略按小样本 -> dev -> holdout 推进。
4. **P3 最终打包**：冻结源码、配置和报告，生成最终候选及校验值。
5. **P4 加分项**：Docker 美化、完整 cgroup/重启矩阵、非阻塞型可观测性增强。

P4 在任何情况下都不能挤占 P0～P3。新的抽象、服务、重构或大篇幅文档只有在阻塞正确性、复现
或提交时才能开始。

## 3. Docker 硬性时间盒

### 3.1 前 10 分钟预检

只检查：

- daemon/Compose 是否可用；
- 是否 rootless，host port 能否发布；
- memory/PID cgroup 是否实际启用；
- 固定基础镜像 manifest 是否能在合理时间取得；
- Python 包源速度是否可接受；
- 磁盘是否足够。

任一硬能力缺失，立即记录事实并转原生部署或正常 daemon，不在当前机器修 Docker。

### 3.2 单阶段最多 30 分钟

一个开发或调测阶段用于 Docker 构建、网络诊断和 daemon 排障的总时间不得超过 30 分钟。达到
上限必须停止，不允许以“再试一次”为由重置计时。

允许的替代路径：

- [B05 非 Docker 部署指南](../batches/B05/NATIVE_DEPLOYMENT.md)；
- memory-api 原生运行，数据库/MemOS 复用已有容器；
- 开发专用源码 bind mount，只重启进程；
- 转移到已知支持端口和 cgroup 的调测机 daemon。

### 3.3 构建次数

- 开发迭代：默认不构建完整镜像；运行源码或挂载源码。
- 修改 memory-api：如必须验证容器，只构建 `memory-api`。
- 修改 MemOS patchset/依赖：只构建 `memos`；普通配置变化不构建。
- Prompt、model ID、URL、Key、阈值等运行配置变化：不得触发镜像构建。
- 代码冻结：最多一次候选构建。
- 独立 clean-room 复现：只有候选已经可评分且环境正常时再做一次。

不得在每轮模型/prompt 实验后构建镜像。最终选择确定前，调测应使用原生路径或源码挂载。

## 4. 下载与缓存规则

- Python 包：第一次慢/失败就使用明确审核的华为、清华或内部源；一次只使用一个显式源，保留依赖
  锁和 hash，不设置不可审计的静默多源 fallback。
- Docker Hub：PyPI 镜像不能加速基础镜像 manifest。频繁跨机器构建时由主机管理员配置可信的
  registry pull-through cache，或使用内部 registry。
- BuildKit：可复用现有 layer；只有多个候选确实重复构建时才增加 local/registry
  `cache-to/cache-from`，不得为“优化缓存”单独花费超过 Docker 时间盒。
- 固定基础镜像和依赖可以预取，但预取失败不阻塞原生开发与调优。

## 5. 调测机启动顺序

调测机收到交接包后严格执行：

1. 校验 commit/ZIP SHA-256，确认工作区和配置来源；
2. 执行 10 分钟环境预检并决定 Docker 或原生路径；
3. 探测实际 model ID、Chat/Embedding 协议、Embedding 维度、JSON、timeout 和 429；
4. 运行单条 Add/Search smoke，再运行小样本 baseline；
5. baseline 可复现后才开始单变量实验；
6. 先优化影响评测分数的变量，再处理同分候选的延迟和资源；
7. 最终候选冻结后才执行一次正式打包/容器验证。

Docker 不通过但原生路径可评分时，必须继续 baseline 和调优，同时把 Docker 记录成并行待办，不能
停下等待容器环境。

## 6. 最小记录，禁止记录本身成为瓶颈

每次实验只强制记录：候选 ID、基准 commit、唯一主变量、模型/非密钥配置、数据切片、分数、
P95/max 延迟、失败数、结论和回退点。无新证据时不重复写长篇设计说明。

以下情况立即停止当前工作并报告用户：

- P0 可评分闭环被新架构问题阻塞；
- 真实 Add 达到 120 秒或 Search 达到 60 秒；
- 出现跨用户泄漏、错误成功、数据破坏或凭据风险；
- 需要修改公共 Schema、Embedding 维度/存量索引或新增服务；
- Docker 时间盒到期且没有可用的原生路径。

## 7. 完成标准

剩余 48 小时的成功标准不是“所有工程项都做到最好”，而是：

- 有一个契约正确、超时内、可启动、可回退的完整候选；
- 有真实模型和真实数据上的 baseline；
- 有少量高置信度、可复现的调优收益；
- 有最终源码/配置/ZIP 身份和最小审计证据；
- 所有未完成的 Docker/服务化加分项被明确记录，但不冒充核心阻塞项。
